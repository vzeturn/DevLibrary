# RT-0298: one agent per customer, attach more products to it

Owner 2026-11-20: a customer may use several or all products (PMS, E-Invoice, Check-In,
Membership, PDAOrder, Hotel Link, SRBackup). One dl-agent covers every product, so a second
product must attach to the agent already installed instead of skipping its code ("Already
enrolled") or replacing the identity (`--reenroll`).

## Design

- Hub `POST /v1/attach` (signed by the agent, PROTOCOL §1): body `{code}`. The code is a normal
  one-time enrol code (product-minted or admin). One D1 batch:
  1. claim the code for the calling agent (`used_by_agent` = the existing agent);
  2. merge the code's `config.modules` into the agent's config with SQLite `json_patch`
     (RFC 7396: other modules and settings stay), version + 1, so the next heartbeat delivers it;
  3. upsert `product_links (agent_id, product)` → the product's tenant, site and code.
  The agent keeps its id, key, tenant, site and channel. An admin code (no product) attaches only
  inside the agent's own tenant (`409 tenant_mismatch`).
- Enrolment with a product code records the same link, so every agent ↔ product pair is known;
  migration 0008 creates the table and back-fills it from used product codes.
- Admin `GET /admin/product-links?agent_id=&product=&tenant_id=` lists links.
- dl-agent: `HubClient::attach`, `dl-agent attach --code` (env `DL_AGENT_ENROLL_CODE`), and
  `dl-agent install` on an enrolled machine with a code attaches instead of skipping. A refused or
  failed attach during install is a warning (re-running an old line with its used code must not
  break an update); `dl-agent attach` itself fails loudly.
- Same one-line installer for every product: unchanged command, the binary decides.
